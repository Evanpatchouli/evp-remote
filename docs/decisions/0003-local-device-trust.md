# 0003 · Local trust for My Devices

**Status** Accepted for implementation on 2026-11-20. The current Windows contract also supports local preapproval when issuing a single-use code. [Remote Assistance](../specs/windows-session.md) · [My Devices](../specs/my-devices.md)

Users need to control their own Windows PCs from a persistent list without a login or a new invitation for every connection. Pair the two clients once with explicit actions on both devices. Each stores the other's public key and its local authorization. A device ID is the SHA-256 fingerprint of its public key. For first pairing, transfer a high-entropy code out of band. The issuing PC either approves the verified request on arrival or preapproves one valid request when generating the code. Subsequent control proves possession of both pinned keys with a fresh challenge and signs the WebRTC descriptions, including their DTLS fingerprints. The receiving PC checks its own trust and permissions before starting capture.

Use the existing signaling deployment for presence and rendezvous, and coturn only as an ICE fallback. Keep presence and in-flight attempts in memory; neither service stores a trusted-device list. Reuse the existing deployment access key once in setup to protect signaling capacity and the TURN budget. It is not a user account or a remote-control credential; a key holder still needs a locally authorized device identity. Keep the configured credential and identity private key protected by Windows user-scoped DPAPI. No public inbound port or service installation is required on a PC.

Local trust allows either PC to revoke its own authorization while offline and avoids creating an account or server-side authorization authority. A new installation without the original key requires pairing again. Removing a device on one side does not edit the other side's list; mutual proof and local checks prevent either direction from reconnecting until both sides trust again. An untrusted signaling broker can still drop traffic, misreport presence, or observe routing metadata; it cannot impersonate a trusted device through signaling alone. Compromised endpoints, leaked pairing codes, and the legacy attended flow are outside this identity guarantee.

See the [behavior contract](../specs/my-devices.md), [wire contract](../architecture/device-signaling.md), and [WebRTC security architecture](https://www.rfc-editor.org/rfc/rfc8827.html#section-9.1).
