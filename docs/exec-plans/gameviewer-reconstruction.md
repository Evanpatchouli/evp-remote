# Independent reconstruction plan for NetEase UU Remote

Based on the [local analysis of Windows 4.48.0.5446](../architecture/gameviewer-analysis.md). The proposed definition of “complete reconstruction” is that the same user tasks can be completed on the same devices, account scenarios, and network conditions, with agreed picture quality, responsiveness, recovery, and permissions. The project uses its own clients, server, and device identities. There is currently no verifiable specification for interoperability with NetEase accounts or clients, byte-for-byte compatibility with the original private protocol, NetEase cloud node coverage, or internal implementations on other platforms.

## 1. First runnable version

The first deliverable is **one P2P remote-control session between two Windows computers on different internet access networks**. For example, computer B uses home broadband and A uses another broadband connection or a mobile hotspot, each with independent internet access. A selects B, and B accepts. A can see a 1080p60 test animation from B, hear timestamped sound, and operate a test application. When B ends the session, picture updates stop and input permission is immediately revoked. 1080p60 is the development starting point.

The first version verifies three outcomes separately: P2P audio and video across networks where direct connectivity is possible; picture delivery after automatic relay fallback when only direct peer connectivity is blocked but the relay remains reachable; and forced relay as a control. The reconstruction reads the final ICE selected candidate pair: either endpoint using `relay` means relay; both using non-relay candidates counts as cross-network direct only after independent internet access is confirmed. Record the path at first frame and subsequent changes. Mark reference-client samples as unknown when the path is not visible. LAN is an optional diagnostic for isolating capture, encoding, and display latency.

| Independent component | First-version responsibility and implementation choice | Data owned |
| --- | --- | --- |
| Controller | C++/Qt windows host the device list, assistance requests, session window, and statistics. D3D11 renders video separately; the foreground window captures authorized input. Start with a native Windows client, then extract a cross-platform session layer | Device presentation, window state, decoding capabilities, and each screen's picture |
| Controlled endpoint | A Windows service manages lifecycle and interactive-session selection; a process in the user session handles display, consent, capture, and device switching. The local user can see connection status and disconnect | Desktop textures, device capabilities, currently granted viewing/control permissions |
| Media engine | Wrap capture sources, encoders, peer connections, decoders, and renderers in C++. Start with H.264 + Opus, falling back if hardware encoding or decoding fails. Use public libwebrtc with our own adapter selection and endpoint integration. [WebRTC native project](https://webrtc.googlesource.com/src/) | Frame lifecycle, media timestamps, stage durations, negotiation results |
| Business logic and signaling | Start with one HTTPS/WebSocket service. Persist accounts, device ownership, and authorization; retain device online state and sessions temporarily. Endpoints exchange descriptions and candidates through it, while business logic can observe both sides independently | Long-lived device identity; short-lived sessions, permissions, expiry, and revocation |
| STUN/TURN | Deploy our own coturn, initially in one region for direct candidates and explicit relay tests; expand based on connectivity rate, RTT, and egress capacity. Media keys remain at endpoints. [coturn](https://github.com/coturn/coturn) · [WebRTC transport](https://www.rfc-editor.org/rfc/rfc8835.html) | Short-lived relay credentials, node health, connection counts and bytes sent/received |
| System devices and business pages | After basic screen and audio work, add virtual displays, gamepads, virtual microphones, and other extensions. Lightweight account and feedback features can use our own web pages; streaming and error recovery retain native entry points | Optional driver and page versions, features enabled by capability |

**Session state.** Record request, awaiting consent, authorized, negotiating, connected, first frame received, controllable, reconnecting, and ended, with distinct reasons for rejection, timeout, revocation, and first-frame failure. Same-account bound devices and one-time assistance each determine their own authorization method. Associate asynchronous events with a session generation; old callbacks and reconnect messages must become invalid after termination. View-only sessions cannot create input, file, or terminal permissions. This reproduces the original UI distinction between “peer online but no picture” and “picture visible but input restricted.”

**Minimum data contract.** `Device` stores identity, public key, and ownership, with leased online status. `Session` stores both endpoints, generation, permission scope, expiry, and end reason. `Capabilities` describes each display source, GPU, codec combinations, formats, and limits. `Track` represents an independent screen or audio source and records source-to-display coordinate mapping. `Stats` records session, track, monotonic-clock time, and stage. Requests in our signaling must support idempotent retries; revocation takes effect immediately on the controlled endpoint and session keys are bound to authorization. A client restarting after a crash must check the current generation with the server.

## 2. Making media and control usable

| Subsystem | Implementation points | Acceptance scenarios |
| --- | --- | --- |
| Screens, windows, and multiple GPUs | Use DXGI Desktop Duplication for desktop capture and Windows.Graphics.Capture for supported window capture. Retain source screen, GPU, dimensions, color, and timestamp per frame; recreate capture on display-mode changes, sleep, or device loss. [Desktop Duplication](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api) · [Windows screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) | Dual-GPU laptop, window across screens, hot-plug, differing scaling, and restore after minimization. Record source and actual encoding GPUs |
| Encoder selection and frame queues | Cache capability probes by GPU, driver version, codec direction, and pixel format. Negotiate the capability intersection, preferring textures on the same GPU; when H.265 is unsupported, first verify H.264 on that GPU. Start with H.264, then add mutually supported combinations such as H.265 and 10-bit. Use bounded preprocessing queues; drop stale unencoded frames under congestion and use frame numbers to distinguish static-scene frame reduction from performance drops | Disable hardware encoding or decoding, change drivers, asymmetric GPUs, HDR/SDR switching, and GPU reset; verify actual negotiation and first visible frame in each case |
| Reception and display | Decode natively to GPU surfaces, reuse allocators where possible, control queueing and synchronization, then present through a swap chain. Record receipt, decoding, presentation submission, and externally observed first frame. Negotiate the complete capture-to-display format chain separately for SDR, HDR, and chroma sampling | Fast scrolling, dark gradients, fine colored text, mouse movement, and window resizing. Statistics must distinguish high-frame-rate decoding from a lower-refresh display |
| Audio | Capture desktop mix with WASAPI loopback, encode/decode with Opus, and use a separate queue and audio clock. Request separate microphone uplink permission. Recreate streams on USB/Bluetooth or default endpoint changes. [WASAPI loopback](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording) | Default output switching, microphone toggle, simultaneous two-way speech, picture without sound, network reconnection, and long-term A/V synchronization |
| Public internet and impaired networks | Use ICE candidate checks, connect directly when reachable, fall back to relay when direct connection fails, and support forced relay for acceptance. Adapt bitrate from feedback, request keyframes, and bound packet queues. Schedule media, time-sensitive input, and large files separately; allow file rate limits. Obtain a shared baseline before evaluating dedicated redundancy or transport extensions. [ICE](https://www.rfc-editor.org/info/rfc8445/) · [TURN](https://www.rfc-editor.org/rfc/rfc8656.html) | Two broadband links, home broadband and cellular, IPv4 NAT, mutually reachable IPv6, restricted UDP, Wi-Fi switching, and sudden bandwidth reduction and recovery. Record selected candidate types, first frame, stalls, and reconnection |
| Input return | Start with standard keyboard and mouse in authorized sessions. Deliver state transitions such as key presses reliably and release them on disconnect; mouse movement may coalesce older events. Input references the display source, DPI, rotation, and frame generation. Separately test gamepad state, repeated events, hot-plug, and reset on disconnect | Negative coordinates on dual screens, remote 150% DPI, portrait screen, disconnect while holding a key, input attempted in view-only mode, windowed and full-screen games |

**Measure latency until the user sees the result.** Complete input-to-picture time includes controller sampling, uplink, controlled endpoint application and refresh, capture wait, encoding, downlink, jitter buffering, decoding, and display scanout. At 60 Hz a frame takes about 16.7 ms; one extra queued frame can change the feel. Film a physical button/indicator and the controller screen together with a high-frame-rate camera and measure button press to pixel change frame by frame. Independent monotonic clocks on the two machines only measure local stage durations; cross-machine one-way latency requires clock synchronization and recorded error.

## 3. Feature alignment checklist

For each row, record the reference version's visible entry point, permitted conditions, success state, failure state, and state after disconnect. Mark features available only as embedded resources or subject to entitlements as pending confirmation. All implementation approaches below are this project's design.

| Feature | Independent implementation | Completion criteria |
| --- | --- | --- |
| Accounts, device directory, assistance | Own accounts and device binding, online leases, assistance invitations, same-account policy, one-time consent, recent connections | Two-account assistance and same-account access work; rejection, cancellation, expiry, repeated clicks, device removal, and stale connections after disconnect have deterministic outcomes |
| Viewing, control, and privacy | Enforce viewing and control permissions on the controlled endpoint; separately manage microphone and file permissions; provide local status, exit, and desktop-setting restoration | Viewers cannot send effective input; after user interruption, local display, mute, lock, etc. return to the selected policy, including after abnormal exit |
| Multi-screen, split screen, second screen, headless host | Separate source and track per physical display; add our own signed IDD for virtual displays, modes, and rotation. Render independent windows and synchronize input coordinates. [Windows IDD model](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/indirect-display-driver-model-overview) | Switch existing screens, display two simultaneously, boot without a physical screen, add/remove a second screen, and retain screen identity after reconnect |
| Gamepad and virtual microphone | Provide supported, maintainable signed virtual gamepad and audio endpoints; negotiate device capabilities and test game compatibility. Low-copy emulator integration requires a public or authorized interface from the target emulator | Games recognize devices, re-enumerate after hot-plug, and reset buttons on disconnect; remote applications select the microphone and receive sound. Test emulator end-to-end frame rate and audio separately |
| Clipboard, drag-and-drop, file tasks | Authorize clipboard by direction and type and prevent echo loops. Use independent task IDs, chunk checksums, persistent progress, cancellation and resume; write temporary files and commit after verification | Chinese and long filenames, zero-byte and large files, name collisions, full disk, cancellation, restart after pause, matching hashes after retransmission, and media meeting its threshold during transfer |
| Terminal and application management | Provide authorized users with independent terminal session listing, creation, opening, renaming, and termination using Windows ConPTY. Application lists support search, selection, removal, and ordering; also record authorized launches and exits. [Windows pseudoconsoles](https://learn.microsoft.com/en-us/windows/console/pseudoconsoles) | Chinese terminal text, resizing, disconnect/reconnect, resource release on termination, and owner revocation. Reopening preserves application order; list removal is clearly distinguished from uninstalling |
| Remote wake and port mapping | First confirm supported topologies on the reference client. Our wake implementation depends on an available LAN wake collaborator and host settings. Port rules apply only to services, scopes, and durations explicitly selected by the device owner; support add, enable/disable, edit, copy, retry, and delete | Test with and without a wake collaborator, unsupported host, rule conflicts, expiry, and revocation. The original backend implementation remains unknown |
| Cloud devices, membership, purchases, messages, support | Own cloud devices support request, queue confirmation/cancellation, timeout requeue, power on/off, and release; cloud disks support automatic mounting, reset, and renewal. Separate entitlement catalog and idempotent ledger; connect messages, feedback, and purchase history to own pages, with offline skeletons and retry | Test inventory covers resource lifecycle; reconcile accounts after provisioning failure; duplicate callbacks grant entitlements once; mount the correct disk; reset requires confirmation; retry after network loss. NetEase inventory, pricing, and scheduling remain unknown |
| Updates, health, crash recovery | Signed updates, staged replacement, commit after health confirmation, and old-version recovery. Monitor UI/business and media heartbeats separately and limit repeated restart frequency | Bad signature, insufficient space, interrupted upgrade, stuck media thread, and login-user switch; paths, versions, services, and authorization state remain consistent after success or rollback |
| Cross-platform clients | Share session, permission, capability, and statistics specifications; adapt macOS and mobile capture/decoding, input, audio routing, and background lifecycle to each platform. Port the viewer first, then controlled endpoints within platform support | Establish baselines by platform × role. Measure first frame and recovery on the same network; separately test mobile foreground/background transitions, touch layout, external gamepads, and display rotation |

Programs and resources scanned on Windows are sufficient to identify these work items. Matching mobile gestures, macOS permission flows, cloud real-device supply, and emulator-specific interfaces item by item requires reference environments for the relevant platforms or suppliers. Keep inaccessible features marked “unverified” in acceptance records and record required device or account conditions.

## 4. Development order and delivery gates

| Phase | Deliverable | Gate to next phase |
| --- | --- | --- |
| 0 · Establish reference baseline | Prepare two Windows machines with separate internet access, two types of authorized accounts, controllable network conditions, test animation and sound. Record versions, GPU/drivers, displays, network, and quality settings | Save records for cross-network connection, restricted direct connectivity, refused assistance, and recovery after disconnect. Identify confirmed and unknown media paths separately. These records have not yet been obtained for this report |
| 1 · Two-Windows end-to-end loop | Own single-region signaling and TURN, device pairing, explicit consent, native picture and audio, basic keyboard/mouse, termination, and statistics. One screen and one video format only | Cross-network direct, automatic relay fallback, and forced relay all complete the first section's scenarios; actual path selection, frame delivery, and permission revocation are observable |
| 2 · Public internet and recovery | Expand public-network routing and fallback; complete expiry/retry, network switching, transport feedback, bitrate adaptation, and file traffic scheduling | First frame appears on restricted networks, reconnection passes, and each failure can be attributed to authorization, signaling, connection, media, or presentation |
| 3 · Windows product features | GPU capability matrix, multi-screen/HDR, microphone, files, clipboard, terminal, gamepad, and virtual display | Cover at least one hardware/software encode, hardware/software decode, and same/cross-GPU combination; drivers and basic features can be upgraded and recovered separately |
| 4 · Other platforms and online services | Mobile or macOS clients, second screen, emulator integration, cloud devices and entitlements, reliable upgrades, and regional capacity management | Meet the checklist item by item, complete A/B comparisons on supported platform/role combinations, and record specific dependencies and alternative scope for blocked features |

**Estimate capacity first, then measure.** For 1,000 concurrent one-way video streams averaging 15 Mbit/s, with 20% of sessions using a single TURN hop, relay video ingress and egress are each about 3 Gbit/s, or about 6 Gbit/s total bidirectional interface traffic. Audio, retransmission, protocol overhead, redundancy, and capacity headroom are additional. Measure regional peaks and separately account for interface load and billable egress. These numbers are illustrative; the original product's relay proportion and bitrates are unknown.

## 5. Determining the degree of reconstruction

The figures below are **proposed initial engineering thresholds**, subject to confirmation after phase 0 obtains reference measurements in the same environment. Preserve reference and reconstruction records separately, grouped by GPU combination, actual direct/relay path, measured RTT, available bandwidth, and display refresh rate. Fix both public-network access links and quality settings for performance comparisons. “Stable cross-network” below means a link between different access networks with no additional injected jitter or loss during the test, sufficient available bandwidth, and little measured RTT variation.

| Item | Measurement | Initial threshold |
| --- | --- | --- |
| Connection and first frame | Both endpoints online and authorized at 1080p60; measure start click to first actually visible frame. Separate cold and warm starts. Run each of the three preset scenarios in section 1 thirty times, retaining failures and final paths | At least 29 attempts per group succeed on the expected path. Also report the proportions of direct, relay, and failure across all automatic-selection attempts, and compare first-frame P95 in the same scenario |
| Control response | Fix both public access links, display refresh rate, and test application. Record at least 100 physical-input-to-pixel-change events with a high-speed camera; compare by actual path and RTT | Under identical conditions, target input-to-display P95 within one display refresh period of the reference; record camera frame-period error |
| Actual picture | Play the same numbered 1080p60 motion image for 10 minutes on both versions; use the same high-speed camera to read unique frame numbers actually displayed by the controller and the longest freeze. Record internal queue values only where obtainable | Mean actual display ≥ 58 fps on stable cross-network links, reporting direct and relay separately. Test static-scene frame reduction separately; compare fine text and color at the same bitrate and source material |
| Impaired network and reconnection | Set baseline RTT to 80 ms; inject 0–20 ms uniform additional jitter and 1% independent random loss only from controlled endpoint to controller. Reduce that direction's bandwidth from 20 to 5 Mbit/s for 30 seconds, then restore it; a five-second bidirectional outage is a separate case | Picture returns within 10 seconds of network recovery and all held keys are released. Record actual send bitrate, longest recovery freeze, and audio interruption; additionally check whether reconstruction queues return to their pre-limit range |
| Audio | Use a synchronized flashing and sounding source; sample a light sensor and microphone at the controller using one clock. Run 30 minutes each on stable and impaired cross-network links, separating endpoint-switch anomalies from continuous drift | Absolute A/V offset P95 ≤ 80 ms on stable cross-network links, with no accumulating one-direction drift during continuous playback; verify system audio and remote microphone separately |
| Permissions and data | Positive and negative cases for same-account access, different-account assistance, rejection, timeout, view-only, and revocation; compare hashes after file completion | Zero new inputs accepted by the controlled endpoint after rejection/revocation; no transfer can start without file permission; all completed file hashes match |

Finally, sign off each row by platform, role, hardware, network, feature, reference result, reconstruction result, and reason for differences. Report Windows basic streaming, enhanced system devices, cloud services, and other platforms separately. The Windows primary path and engineering approach can currently be identified; planned performance figures and cloud-service coverage cannot be counted as implemented results.
